# Adaptive hiring and runtime selection

Choose the assignment and evidence standard before choosing its runtime. Job levels describe ownership, autonomy, ambiguity, and consequence; they are not model tiers. A principal title does not force a flagship model, and a junior title does not justify a weak configuration for difficult work. Apply the same decision process to delivery, research, integration, and independent acceptance.

## Decide each hire

1. Identify the actual work: bounded execution, routine implementation, open investigation, difficult reasoning, cross-system integration, or consequential acceptance. Consider context breadth, required tools, uncertainty, failure cost, and how cheaply mistakes can be detected.
2. Inspect the live delegation tool's available models, descriptions, supported effort values, context behavior, and override restrictions. Treat that contract as authoritative. Respect user-selected models and project constraints. Do not retain a hard-coded model roster or infer capability from names, family numbers, role titles, or effort labels.
3. Choose the smallest configuration with a credible path to the required evidence. Inherit the parent model and effort when they fit and there is no concrete reason to override. Consider an available faster model for prescribed, easily checked work; consider a more capable model for unresolved ambiguity, consequential reasoning, or demonstrated reliability problems. Strong verification can support a leaner delivery hire, but cannot compensate for inadequate judgment in the verifier.
4. Select effort separately from model identity. Use the runtime default when adequate; raise supported effort for multi-step reasoning or difficult unresolved questions. Do not force every hire to low effort, impose title-based floors, or reserve higher effort solely for particular titles. Higher effort is not proof of correctness and may not fix missing context, tools, or a poor task brief.
5. State a concise hiring reason and escalation trigger. Record what would change the decision: failed acceptance, repeated reasoning errors, an unexpected interface, or evidence that the work is simpler than assumed. Do not invent benchmark rankings, costs, latency, or savings; use available observations and label unknowns.

For material choices, compare the inherited configuration with the most plausible alternative. One sentence is enough; do not run a benchmark or hire a scout merely to choose a model. If capability is unclear, use a bounded discovery assignment or a small representative check when it adds value. Do not queue work merely because an old model name is unavailable; queue only when no available configuration can credibly meet the assignment's requirements.

## Context and spawn configuration

Choose context from the assignment's needs. Use a self-contained brief with `fork_turns="none"` when accepted artifacts and a concise handoff suffice. Use a supported partial fork for relevant recent context, or full inheritance when the conversation contains necessary decisions that are costly to reconstruct. Avoid oversized transcripts, but do not discard essential constraints to force a model override.

Under the current collaboration contract, omitted or `"all"` forks inherit the parent model and effort and cannot accept overrides. For inheritance, omit `model` and `reasoning_effort`; for an authorized override, use `"none"` or a supported positive partial fork and pass only supported settings. Recheck the live contract instead of assuming these rules are permanent. This skill authorizes task-appropriate overrides when invoked, subject to higher-priority instructions.

For each distinct assignment, record role, ownership level, chosen or inherited runtime, context choice, owned output, hiring reason, and escalation trigger. Check actual spawn arguments against this decision. Record observed settings only if exposed; requested settings are not proof of the model actually used.

## Reassess from evidence

When an assigned agent fails its completion or acceptance criteria, the Manager owns recovery. Inspect the failure evidence promptly. Fix missing inputs, unavailable tools, or contradictory instructions first; a stronger model cannot repair those conditions. If the failure reflects reasoning, judgment, or reliability, promote the replacement's model capability and reasoning effort where supported rather than repeating the failed configuration unchanged. A material failure can justify immediate promotion; do not require two failed attempts before escalating. For a minor, clearly local mistake, one bounded correction at the same configuration is reasonable; if it fails again, promotion is required.

Choose promotion from the live model descriptions, supported effort values, and observed results. Do not use a fixed model ladder or assume newer names mean stronger capability. Increase both capability and effort when suitable options exist; if only one can increase, increase that dimension and record the limitation. At the highest suitable model or effort, change the task decomposition, specialist perspective, or verification approach instead of retrying indefinitely. If no credible recovery remains, report the blocker and preserve completed work.

Give the fresh replacement the failed acceptance criterion, concise failure evidence, valid artifacts, relevant constraints, and a concrete completion test. Record the previous and promoted configurations and the reason. Require the replacement to demonstrate that the failed criterion now passes, with independent acceptance where required. Do not treat promotion itself as evidence of success.

A follow-up may complete or correct the original assignment, or safely reuse a suitable idle delivery agent before or at capacity under [operating-model.md](operating-model.md), but cannot change runtime settings. A changed runtime requires a fresh agent unless the live tool supports changing it; preserve accepted evidence and a concise handoff. If capacity blocks promotion, apply capacity recovery and report the unmet requirement rather than silently retrying the failed configuration. Preserve valid work when replacing an agent. Use a simpler configuration for a subsequent bounded assignment when evidence supports it; do not restart completed work to save hypothetical usage.

Independent acceptance remains a separate ownership boundary. Choose its runtime for the judgment required, not automatic model parity with the implementer. Inspect artifacts and perform appropriate independent checks; a stronger model or different persona alone does not make evidence independent.
