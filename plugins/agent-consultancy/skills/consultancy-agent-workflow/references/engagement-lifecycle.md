# Discovery and delivery

Use this reference when unresolved choices materially affect scope, product direction, architecture, or acceptance. It is not an additional sign-off gate for already-authorized work.

## Discover and decide

The Manager owns user questions and scope decisions. Delegates can research options and identify missing decisions. Preserve explicit goals, constraints, and settled preferences. Treat factual claims and proposed solutions as hypotheses where evidence could change feasibility or delivery, without reopening an explicit technology choice merely to suggest alternatives.

Ask only questions whose answers materially change the plan and cannot be established by inspection. Continue independent authorized work while awaiting answers. Use the question tools and collaboration mode actually available; a skill cannot switch the host into a different collaboration or approval mode on its own.

Proportionate research can test feasibility, relevant operational/accessibility/security/maintenance risks, a credible alternative, and what would change the recommendation. Separate confirmed evidence, inference, and remaining proof; avoid overlapping challenge roles without a concrete purpose.

When a user decision is needed, present the recommended option, material alternatives and tradeoffs, scope, acceptance evidence, and unresolved dependencies. Respect prior authorization: seek a new decision only for an unresolved material choice, scope expansion, or an action that actually requires additional authorization. Unanswered assumptions are not approval.

For communications, establish audience, destination, and whether a draft or actual sending/publication is requested. Delegation alone never authorizes external messages.

## Deliver and close

Continue through authorized milestones, recovery, and verification. Return to the user when a necessary decision or authorization is missing, not simply because a milestone finished. Update decisions and ownership in the operating log.

Define how success and impact will be measured alongside the outcome and acceptance criteria, not only after delivery: the observable signal of value — what changed, for whom, and how it will be checked — not just task completion. Prefer real outcome evidence over a proxy, and label a proxy explicitly when no real signal is available. This is separate from the usage audit's efficiency focus in [usage-audit.md](usage-audit.md): one measures whether the delegated work was cheap, the other whether it mattered.

Create a persistent goal only on an explicit user request for one. Do not infer that request from ordinary instructions to finish or continue. If requested, define the end state, constraints, verifiable completion criteria, and stopping conditions; if the host provides a persistent-task or goal-tracking tool, follow its live rules for status changes and budgets. A persistent goal does not expand authority.

Have the integration and independent acceptance owners verify their outputs, then synthesize the evidence and disclose residual uncertainty. Follow the operating model's handoff and skill reuse checks.
